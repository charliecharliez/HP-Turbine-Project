# Turbine design project roadmap

## Purpose and use

Create a modular, iterative turbine-design program that evaluates and optimizes feasible transonic high-pressure turbine candidates. The active workflow runs from boundary conditions through meanline, row losses, airfoil geometry, selected-candidate 2D CFD, and optimization. Cooling and the AMBRA test proposal remain documented as deferred work, not prerequisites for the current optimizer end goal.

- In a future chat, name the task ID and title, review its prerequisites and discuss the approach before implementing it.
- The task order is a suggested dependency order, not a requirement to finish every item in a phase before starting another. Revisit upstream decisions when later evidence requires it.
- Each task's **Done when** describes its intended deliverable or check, not a claim that it already exists.
- The authoritative requirements are in [Project Instructions Email.pdf](./Project%20Instructions%20Email.pdf). Resolve any conflict in favor of that document.

## Active end goal

The program should take validated boundary conditions and candidate design inputs, then repeatedly evaluate and refine the design:

1. Establish the operating boundary conditions and applicable feasibility constraints.
2. Solve the meanline for the candidate design.
3. Calculate blade-row losses and feed them back into the meanline until the coupled solution converges or is explicitly reported as non-converged.
4. Generate airfoil geometry from the current flow/design state and update it as the design is refined.
5. Use 2D CFD on selected, screened candidates to check and improve the airfoil and meanline predictions, then re-evaluate the candidate.
6. Search the feasible design space and report results for three distinct modes: maximize efficiency, maximize power output, or optimize both and return the efficiency–power Pareto frontier.

All active roadmap tasks should build, verify, or integrate a part of this workflow. The candidate evaluator and optimizer must retain inputs, assumptions, convergence status, infeasible/failed candidates, warnings, and results so comparisons are reproducible. Use lower-cost meanline/loss/geometry evaluations to screen candidates; do not require a CFD solve for every optimizer iteration.

Cooling models and the AMBRA test proposal are deferred and are not blockers for this active end goal. Until cooling work is resumed, the program must not claim thermal feasibility against the metal-temperature limit or full project compliance. The 2D CFD design validation remains in scope.

## Progress snapshot

Status is assessed against each task's **Done when** criteria. **Partial** means a relevant implementation or test exists but the full deliverable or its validation is outstanding. **Not started** means no relevant implementation was found in the reviewed workflow. **Deferred** and **Optional** retain the scope choices above. No task is treated as complete merely because a prototype returns a result.

The current branch couples the single-stage meanline, radial-equilibrium, blade-row geometry, and Kacker–Okapuu loss modules in `src/stage_solver.py`. It iterates loss coefficients, reports stage performance and spanwise values, and checks a limited set of uncooled constraints. `src/design_sweep.py` screens and refines single-stage designs for total-to-static efficiency. This is meaningful integrated prototype progress, but it is not the required one-/two-stage, three-mode, CFD-informed optimizer.

- Shared design models validate boundary conditions, row/stage inputs, and run-record shapes; the data model can represent multiple stages and coolant states, but those shapes are not an integrated multi-stage or cooling solver.
- The gas-property module obtains CoolProp values at inlet and isentropic exit conditions, averages `cp`, and derives a consistent effective `gamma` from that `cp` and air `R`. This remains a constant-property approximation; properties are not propagated row by row or through coolant mixing.
- Blade-row geometry is generated at hub, midspan, and tip and passed to loss calculations. Chart loading, interpolation, selected interface behavior, velocity-triangle relations, continuity, meanline energy closure, rotor rothalpy, and pressure-based efficiency relations have focused regression tests; these do not constitute full independent validation of every physical model.
- `src/run_meanline.py` has input validation, JSON run-record handling, and per-rotor hardware checks, but the current full test run finds six errors in that path: it accesses `Inputs.Beta3_metal`, which is not present on the current `Inputs` model (`beta_3` is the available field). The standalone runner and its tests therefore need repair before this record path can count as reliable evidence.
- The default stage design violates the blade-speed constraint; tests also exercise a selected single-stage design that passes the constraints currently implemented. Constraint coverage remains incomplete: cooling and metal temperature are not checked, and the active stage loop is not a two-stage evaluator.
- Verification run from the repository root with `.venv\\Scripts\\python.exe -m unittest discover -s tests -v`: 46 tests ran, 40 passed, and 6 errored in the `run_meanline` path described above.
- CFD cases, grid studies, cooling calculations, and AMBRA analysis were not found in the reviewed source. Cooling and AMBRA remain deferred; required 2D CFD remains active and outstanding.

`PROJECT_REQUIREMENTS.md` contains references to roadmap task IDs A01–A03 and B02–B03 that have no corresponding task definitions here. Keep this traceability gap visible rather than inferring that those requirements are complete.

## A. Requirements and foundations

- **A05 - Make runs reproducible and errors visible.** Define how to run modules and record inputs, assumptions, warnings, convergence status and results; reject invalid or infeasible designs explicitly. **Status: Partial** — run-record and hardware-check foundations exist, but the standalone runner currently errors on an obsolete input-field name and overall feasibility checks remain incomplete. **Done when:** another user can repeat a run and distinguish failure from a valid result.

## B. Repair and validate existing foundations

- **B04 - Audit the existing meanline physics.** Check thermodynamic states, relative-frame quantities, rothalpy, Euler work, continuity, angle signs and assumptions against references. **Status: Complete** — the audit found that separately averaging inlet/exit `cp` and `gamma` violated `cp = gamma R / (gamma - 1)` by about 0.10%; the default effective `gamma` is now derived from averaged `cp` and air `R`. Regression checks cover stator total temperature and continuity, signed velocity frames, rotor rothalpy across unequal radii, Euler/thermodynamic work, reaction, total pressure, and efficiency relations. The solver still uses a constant-property approximation; row-wise variable properties remain C01 work. See [DESIGN_CONVENTIONS.md](./DESIGN_CONVENTIONS.md) and [the ASME rothalpy reference](https://asmedigitalcollection.asme.org/GT/proceedings/GT1992/78934/V001T01A078/238713). **Done when:** identified issues are resolved or explicitly documented and independent checks pass.
- **B05 - Audit existing radial-equilibrium physics.** Check governing assumptions, streamline mapping, pressure integration, mass conservation, meanline matching and vortex-law limits. **Status: Complete** — the rotor-exit axial-velocity profile now includes the radial variation in Euler work required by radial equilibrium. Tests verify the ideal-gas pressure/temperature entropy relation and vortex-law shape derivatives for free-vortex, exponential, and first-power laws; mean-radius pressure and swirl anchors across those laws; free-vortex mean-radius state matching; and reconstructed local-density mass flow within 0.1% for representative designs. Continuity is still calibrated with meanline density, properties use constant `cp`/`gamma`, and no external benchmark was available; these checks verify internal model consistency, not experimental validity. **Done when:** representative cases and limitations are verified.
- **B06 - Audit Kacker-Okapuu implementation.** Check digitized charts, coefficient definitions, corrections, applicable ranges and tip treatment against the original method and an independent reference. **Status: Complete** — Fig. 6 hub-to-mean Mach factors now use interpolation of the digitized values with out-of-range warnings instead of the prior power-law approximation. Focused checks cover the Fig. 1/2 profile charts, hub shock, secondary loss, Reynolds/Mach corrections, Fig. 14 trailing-edge conversion and bounds, and the separate unshrouded-rotor tip-efficiency debit. The original paper remains authoritative where the public TurboFlow implementation uses a simpler trailing-edge conversion; its Aungier correlations and loss implementation were used only as cross-checks, not experimental validation. See [VERIFICATION.md](./VERIFICATION.md). **Done when:** individual loss components and warnings have defensible reference checks.

## Key dependencies and decision points

- Requirements, conventions, shared models, engineering-invariant tests, gas-property unit conversion, loss-chart loading and single-stage hardware checks establish foundations. The A05 run-record path currently has a test-blocking field-name mismatch, and downstream constraints remain incomplete. Physics audits **B04-B06** should inform implementation.
- Candidate evaluation depends on validated boundary conditions and gas properties (**A05**, **B04**, **B05**, **B06**, **C01**), then meanline and row losses (**D02-D05**, **E01-E03**) coupled with actual row geometry (**G01-G06**). Spanwise design (**F**) informs hub, midspan and tip constraints and geometry.
- Optimization (**E04-E05**) follows the validated candidate evaluator. It compares stage count and other design variables in the three objective modes; selected candidates proceed to 2D CFD (**H**) and CFD-informed refinement before final comparison.
- Integrated reporting and verification (**J01-J05**) depend on traceable candidate runs and validated model outputs. Cooling (**C02-C06**) and the AMBRA proposal (**I01-I05**) are deferred and are not dependencies of the active optimizer workflow.
- Decisions such as cooling correlation, CFD solver, vortex law, and optimizer implementation details remain for their dedicated tasks.
